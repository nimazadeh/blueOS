# ADR-013 — Internationalization & RTL

- **Status:** Accepted
- **Date:** 2026-09-09
- **Supersedes:** none

## Context

Persian/RTL is a first-class requirement. The brief warns against building LTR first
and "flipping" later. Content types (products, posts, case studies) need localized
text; mixed LTR technical strings (product names, code, URLs, emails) must stay
correct; URLs and SEO must be locale-aware.

## Decision

- **Locales:** `en` (default) + `fa` enabled in v1. `APP_DEFAULT_LOCALE` configures
  the unprefixed default; other locales get prefixed URLs
  (`/fa/…`). Routing resolves locale from prefix → session/cookie → header.
- **Layout direction is applied at `<html dir="rtl" lang="fa-IR">`** from the
  locale, with **all styling via CSS logical properties** (`margin-inline-start`,
  `padding-inline`, `inset-inline-*`, `border-inline-*`, `text-align: start`).
  No `*left/*right` properties in component CSS.
- **Directional icons:** arrow/chevron icons flip via `[dir="rtl"]` transform or
  direction-aware icon component; controls (drawer position, back buttons, sliders)
  mirror naturally through logical properties/start-end placement.
- **Typography:** Persian uses **Vazirmatn** (self-hosted via npm) as the `fa` font
  stack with taller line-height (1.7–1.8) and **no uppercase/wide tracking for
  Persian labels**; Latin stack for `en`; mono for code with LTR isolation.
- **Localized content:** JSON translation columns `{en, fa}` with `Translation`
  accessor + fallback to `en`; admin editors render per-locale tabbed fields.
- **Mixed content rules:** `dir="ltr"` + `unicode-bidi: isolate` on code, URLs,
  emails, versions, English product names inside Persian text; `dir="auto"` for
  user-generated display text.
- **Numerals:** Persian digits (via `fa-IR` locale formatting) for editorial
  numbers; **Latin digits preserved** in versions, URLs, prices-as-displayed,
  technical identifiers. Config `site.numeric_locale`.
- **SEO:** per-locale metadata, `hreflang` alternates, `x-default`; sitemap per
  locale; canonical per locale URL.

## Alternatives considered

1. **Build LTR, flip with CSS transforms** — rejected by brief; transforms break
   text/bidi semantics.
2. **i18n library (Laravel lang + `__()`)** — used for **UI strings** (validation
   messages, buttons); **content strings** live in DB JSON columns (manual
  locale handling for content is more appropriate than translation files that
   would require code deploys).
3. **RTL via `dir` flip library (rtlcss)** — rejected: logical properties are
   native, testable, and don't require build-time duplication.
4. **Persian-only site** — rejected: brief implies bilingual positioning.
5. **Latin numerals everywhere** — rejected for editorial polish; mixed rule chosen.

## Consequences

- ✅ RTL is a property of the design system from token #1; no rework later.
- ✅ Mixed-direction technical content handled by explicit isolation rules.
- ⚠️ Every new component must use logical properties (enforced in review + tests).
- ⚠️ Admin editors need per-locale input tabs (small extra UI cost, intended).
- ⚠️ `fa` content must be entered by a real Persian editor; empty locales use `en`
  fallback (documented fallback behavior).
